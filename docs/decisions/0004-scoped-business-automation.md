# ADR-0004：以范围授权驱动业务自动化

- 状态：已接受
- 日期：2026-09-01
- 替代范围：ADR-0001、ADR-0002 和 ADR-0003 中“必须在 preview 后由当前消息逐项确认”的限制

## 背景与目的

freee MCP 的目标是成为自动化流程中的可靠执行组件，而不是复制网页上每一次确认。此前所有写操作都采用 prepare、展示 preview、等待一条新的用户确认、再 commit 的交互模式。这适合偶发的单项操作，但会让明确的多日期处理、条件式审批和定期自动化反复中断；用户还被迫接触本应由 Agent 校验的 SHA-256 fingerprint。

用户真正需要授权的是业务结果、适用范围和判断条件，而不是某个内部 hash。MCP 应允许 Agent 在已获授权的边界内自动完成逐项 prepare、fingerprint 校验、commit 和写后验证，同时继续由代码强制执行 freee 状态检查和业务依赖。

## 决定

### 1. 授权业务意图，而不是 fingerprint

一次有效授权可以是：

- 精确的单项指令，例如在指定日期打卡、提交一条指定申请或处理指定申请编号。
- 当前运行中的范围策略，例如对指定日期集合创建 `勤務時間を削除` 申请，或按明确条件审批/差戻し所有匹配项。
- 已明确配置的定期自动化调用，其每次调用都携带完整的身份、范围、动作、条件、上限和终止规则。

如果用户当前消息已经完整、明确地要求执行这些写操作，Agent 不得只因 prepare 在后续完成而再次索要确认。`confirm: true` 和 CLI `--confirm` 表示 Agent 断言当前 commit 与该精确指令或仍然有效的范围策略一致；它们不是要求用户查看或复述 fingerprint 的信号。

“查看”“调查”“测试”“帮我看看”或没有明确写入结果的请求不构成写授权。实现、测试和发布本项目也不授权任何真实 freee 操作。

### 2. 范围策略覆盖所有已实现的业务写入

同一授权模型适用于：

- 本人打刻。
- 本人月次勤怠提交或取下げ。
- 本人休暇／勤務時間修正的创建、取下げ和取消申请。
- 一般管理者审批或差戻し。
- 专用 `月次勤怠締め` 审批或差戻し。

策略按需要明确：身份或公司、动作类别、目标日期／期间／候选条件、理由或评论、数量上限或终止条件、依赖顺序、失败处理，以及是否授权后续步骤。只有当最终结果被明确包含时，一项策略才可以覆盖“创建申请后再审批”等链式操作；仅要求提交本人申请不自动授权管理者审批。

若用户的原始指令已精确给出这些边界，Agent 直接使用它，不再强制“复述后再确认”。若存在会改变执行结果的歧义，Agent 只针对缺失边界询问一次。

### 3. 内部仍逐项执行和验证

不新增绕过单项安全检查的批量写接口。Agent 使用现有单项工具顺序执行：

1. 读取权威状态或全部分页候选。
2. 对一个候选调用 prepare。
3. 根据完整结构化 preview 再次判断它是否落在授权范围内。
4. 由 Agent 保存和匹配 fingerprint，并以 `confirm: true` commit。
5. 检查写后验证结果，再处理下一个独立候选。

用户无需复制、比较或逐项确认 raw fingerprint。策略可以覆盖运行中后来发现的项目，但仅限其明确的日期、条件、扫描方式和终止范围。MCP Server 不持久化授权策略；Agent 或调用它的自动化运行必须保存该上下文。

### 4. 已知变化可以重读，未知写入绝不重试

若 commit 在点击前返回明确的 preview-changed 错误，表示没有业务写入。Agent 可以重新读取、重新 prepare、重新判断策略；只要新 preview 仍满足同一授权，就可以继续，无需再次询问。

若点击后的结果未知、输出缺失或无法唯一验证，绝不重试同一目标。Agent 仅用只读工具核实；不能唯一恢复成功时隔离该目标和依赖它的链路。独立项目可以继续，除非身份／backend 改变、授权过期或变得不清楚、分页或页面状态不可信，或出现影响后续判断的系统性错误。

### 5. 保留代码强制的安全与业务不变量

范围授权不会放宽以下条件：

- 每次 commit 仍要求 `confirm: true`、匹配的 fingerprint、正确身份／backend、动作可用和写后验证。
- 批准 `休暇` 前仍必须扫描全部 pending 页，并先处理同员工同日期的 pending `勤務時間修正`；无法可靠匹配时 fail closed。
- `月次勤怠締め` 必须用 freee 页面显示的支付月／工作月关系，任何歧义都 fail closed。
- `勤務時間を削除` 必须选择精确的 freee 控件并验证生成的申请，不能用模糊文本或列表顺序猜测。
- 密码、Token、Cookie、OAuth、Keychain 或浏览器配置写入不属于普通业务自动化策略，除非用户对该配置操作另行明确授权。

## 客户端审批配置

Codex 项目配置继续以 `default_tools_approval_mode = "writes"` 保护未来或未审查的写工具，并仅对上述已审查的七个业务 commit 工具设置 tool-level `approval_mode = "approve"`。这样客户端不会在 Agent 已验证授权策略后再次逐项弹窗；Server 的 `confirm: true`、fingerprint、状态和业务校验仍是必经条件。

## 结果与限制

优点：

- 明确的多项和条件式任务可以不中断地成为自动化链路的一部分。
- 用户只需表达希望得到的结果和边界，不必管理内部 fingerprint。
- 单项状态复核、依赖检查和未知结果隔离仍然有效。

限制：

- 当前没有 Server 端持久化 policy、跨运行撤销机制或独立审计日志；调用方必须在每次运行中携带授权上下文。
- 当前没有事务性批量 endpoint；部分成功会逐项报告，不能原子回滚。
- Claude Code 等其他宿主可能有自己的工具审批界面，需要在宿主侧应用等价配置才能完全避免重复提示。
