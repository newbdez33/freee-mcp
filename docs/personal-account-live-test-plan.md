# 个人账号真实环境测试方案

- 状态：待确认草案
- 适用账号：维护者本人同时拥有员工和审批权限的 freee 账号
- 测试后端：仅 Playwright
- 初始基线：PR #11 合并后的 `main`；包含 `v0.3.3` 之后尚未发布的改动

## 测试目标

只使用维护者本人的勤怠和申请，对已经实现的 freee MCP 功能进行端到端验证。该账号可以提交本人的申请、作为审批人处理自己的申请，并且在发生意外时通过 freee 网页手工修复本人的勤怠。

能够修复不代表允许无人监督地执行写入。每一次真实写入都必须经过独立的安全检查点：prepare、展示并审核预览、在当前消息中明确确认、只 commit 一次、立即读取并验证结果。

恢复勤怠数值并不会删除工作流历史。批准过的勤務時間修正可能继续作为审批记录存在；差戻し的休假申请也可能一直可见，直到在 freee 网页手工删除或清理。所有测试申请都使用可识别的测试理由，便于之后查找。

## 测试范围与排除项

本方案覆盖 [`live-validation-checklist.md`](live-validation-checklist.md) 中可以使用当前个人账号和 Playwright 后端完成、但尚未完整真实验收的申请与勤怠管理功能。

本方案不尝试验证：

- 任何 Public API 功能，包括 OAuth、Token 刷新、API 权限、API 后端隔离和 API 打卡；
- 任何真实打卡操作，包括上班、休憩开始、休憩结束和下班；
- 残業申请：当前公司没有启用 `残業` 表单；
- 本人申请第 2 页：当前历史记录尚未自然超过 50 条；
- 多公司选择：需要一个同时具有多个员工身份的账号；
- 点击业务按钮后的网络故障处理：故意制造生产环境中的结果不明状态并不安全；
- 尚未实现的多段勤務/休憩、员工日明细、删除、批量操作和审计日志。

## 需要准备的测试记录

实际日期只在执行前完成只读检查后确定。

| 编号 | 用途 | 日期选择规则 | 预期最终状态 |
| --- | --- | --- | --- |
| `PA-LW` | 创建休假并由申请人撤回 | 尚无申请的未来工作日 | `差戻し` |
| `PA-LR` | 创建休假并由管理员差戻し | 另一个尚无申请的未来工作日 | `差戻し` |
| `PA-WT-A` | 应用一条勤務時間修正 | 当前仍可编辑的勤怠期间内的过去日期 | 临时为 `承認済` |
| `PA-WT-R` | 恢复原始勤務时间 | 与 `PA-WT-A` 相同日期，使用事先记录的完整原值 | `承認済`，勤怠数值恢复 |
| `PA-M` | 月次提交及撤回 | 所有勤怠测试完成后的可申请月份 | 能撤回时最终为 `差戻し` |

申请理由使用容易识别的形式，例如 `freee-mcp validation PA-LW 2026-08-13`。不得包含凭据或无关的个人信息。

开始 `PA-WT-A` 前，维护者必须从 freee 网页手工记录该日期原始的出勤、退勤和全部休憩时间。MCP 目前还不能读取完整的个人单日记录，因此恢复时不能依赖记忆或推测。

## 全局执行规则

1. 每次只执行一个测试案例。要求执行整份方案，不等于授权其中任何一次 commit。
2. 每次真实 commit 前必须展示：
   - 测试编号；
   - 后端和 MCP/软件包版本；
   - 准确的申请 No.、日期或期间、操作及填写值；
   - 预期影响和恢复方式；
   - 指纹前 12 位。
3. 等待用户在一条新的当前消息中明确确认该测试编号。
4. commit 只调用一次。结果不明时绝不重试。
5. commit 后立即读取同一对象的准确状态；适用时核对列表数量和申请 No.。
6. 如果结果不明，停止自动化，转到 freee 网页确认，并在需要时手工修复。
7. 验收记录中不得暴露凭据、Token、Cookie、浏览器 profile 文件或完整员工表格。

## 阶段 0：候选版本与基线

发布新版本之前，先在源码目录执行本阶段。

1. 记录 Git commit 和当前 package 版本。
2. 运行完整自动化测试、分发校验和软件包 smoke test。
3. 使用 Playwright 后端执行只读状态检查，并确认不会回退或切换到 API。
4. 记录本人申请 `pending`、`returned`、`approved` 和 `all` 的当前数量。
5. 记录管理员待处理数量和月次状态。
6. 初步选择 `PA-LW`、`PA-LR` 和 `PA-WT-A` 日期，并确认不存在目标日期相同的既有申请。

通过标准：所有读取在指定后端成功，或者返回已经记录过的权限/能力错误；freee 数据没有变化。

## 阶段 1：无写入与安全拒绝测试

### 1A：缺少确认

在不提供确认的情况下调用当前可用的各类 commit：

- 当前月次状态允许的操作；
- 创建本人申请；
- `PA-LW` 创建后测试本人撤回；
- `PA-LR` 创建后测试管理员批准/差戻し。

预期结果：MCP Schema 拒绝或返回 `CONFIRMATION_REQUIRED`，并且发生在浏览器启动或业务按钮点击之前。测试前后的相关状态必须完全相同。

### 1B：过期或错误指纹

对每一组当前可用的 Playwright 申请类 prepare/commit，先正常 prepare，然后在其它输入保持不变的情况下，使用一个故意错误的指纹调用 commit。排除全部打卡操作。每一个错误指纹测试也必须单独说明并获得确认，因为如果安全检查本身存在缺陷，理论上仍可能产生写入。

预期结果：返回对应的 `*_PREVIEW_CHANGED`，freee 状态不变。创建本人申请时可能会重新打开并填写尚未提交的表单，这是允许的，但不得点击 `申請`。

如果错误指纹测试意外创建或修改了数据，将该案例标记为失败，停止之后的自动化，查明准确的新状态，并按照该案例预定的恢复方式处理。

### 1C：只读表单变体

只 prepare，不 commit：

- 每一种当前启用的休假类型，包括半休和特别休假；
- 初始日历月份之外的目标日期；
- 不带休憩和带一段完整休憩的勤務時間修正；
- freee 当前月份内的 team status 日期，以及另一个月份应返回的日期不匹配错误。

通过标准：返回值中的选择与目标完全一致；如果变体出现额外必填字段，程序必须识别并停止，而不是忽略；本人申请数量保持不变。

## 阶段 2：本人休假申请生命周期

### 2A：`PA-LW`——创建、读取及本人撤回

1. 读取未来测试日期的可用选项，选择一个准确的全日休假标签。
2. prepare 创建，并展示完整预览。
3. 获得明确确认后，只 commit 一次。
4. 验证只新增了一条申请 No.，状态为 `申請中`、`未承認` 或 `承認済`。
5. 如果已经自动批准，停止本案例，按照下文的已批准休假手工清理流程处理，不尝试撤回。
6. 如果仍在等待批准，验证本人 pending 列表、详情字段和 `withdraw` 可用性。
7. 对该 No. 执行缺少确认和错误撤回指纹测试。
8. prepare 正式撤回并展示预览。
9. 获得明确确认后，只 commit 一次。
10. 验证同一 No. 状态为 `差戻し`，出现在 returned 筛选中，并且不再提供 `withdraw`。

本案例覆盖 `LV-W05`、`LV-W07`、`LV-R01`、`LV-R02`，以及 `LV-S01`/`LV-S02` 中的本人撤回部分。

### 2B：`PA-LR`——创建并由管理员差戻し

1. 在另一个未来日期创建第二条全日休假，仍使用 prepare/确认/commit 流程。
2. 在管理员 pending 列表和详情中验证同一个 No.。
3. 执行缺少确认和错误 return 指纹测试。
4. prepare `return`，展示申请人、No.、类型、日期、内容、理由、检查结果和指纹。
5. 获得明确确认后，只 commit 一次。
6. 验证管理员视图和本人视图中的同一 No. 都为 `差戻し`。

本案例覆盖 `LV-W08`，以及 `LV-S01`/`LV-S02` 中的管理员差戻し部分。管理员批准不需要重复，因为申请 No. `10023` 已经提供过真实批准证据。

### 已批准休假的取消

MCP 已实现 freee 官方 `取消申請` 流程，但这不是直接删除原申请。先从已批准的原申请生成取消预览，展示原 No.、状态、类型、日期、内容、取消理由、审批路径和指纹；单独确认后提交一次，并记录返回的新取消申请 No.。如果该取消申请仍待审批，再以新 No. 执行管理员 prepare/确认/commit。最后分别读取新取消申请与原休假，确认原休假确实已经取消。任何未知结果都不得自动重试；返回/草稿申请的删除仍需手工处理。

## 阶段 3：勤務時間修正及准确恢复

选择当前仍可编辑、尚未最终締め的勤怠期间内的一天。

1. 维护者在 freee 网页记录完整的原始勤怠数值。
2. 将 `PA-WT-A` 设为一个最小但容易观察的变化，例如只把退勤时间移动 1 分钟，其它所有值保持原样。
3. 单独确认后，prepare 并 commit 勤務時間修正申请。
4. 如果申请处于 pending，再次单独确认后 prepare 并批准；如果自动批准，则直接从结果状态继续。
5. 同时验证申请状态和勤怠日历中的实际数值。
6. 立即使用步骤 1 记录的准确原值定义 `PA-WT-R`。
7. 通过独立的确认检查点 prepare、commit 并批准恢复申请。
8. 验证每一个勤怠值都与原始基线完全一致，并确认月度汇总没有残留变化。

如果没有足够时间在同一次监督会话中完成恢复，则不得开始本阶段。如果任何写入返回结果不明，先在 freee 网页检查，再判断是否仍需提交恢复申请。禁止使用推测值恢复。

本案例覆盖 `LV-W06`，并验证申请批准后是否真正修改勤怠，而不只是验证工作流状态。

## 阶段 4：月次提交及撤回

本阶段必须最后执行，且目标月份的所有勤怠修改都已经恢复。freee 的月次締め申请批准后，员工不能再自行录入该月勤怠，因此不能在勤怠修改测试之前执行本阶段。

1. 在 freee 中选择一个显示 `未申請` 且没有未解决勤怠问题的可申请月份。
   如果 Playwright 专用 profile 显示的是另一个月份，使用可见模式打开并手工选择目标月份；当前实现有意不自动切换月份。
2. 读取月次状态并 prepare 提交。
3. 执行缺少确认和错误指纹测试。
4. 展示期间、目标月份、审批路线、审批步骤、检查结果和指纹。
5. 获得明确确认后，只 commit 一次。
6. 验证只有一条匹配申请，状态为 `pending` 或 `approved`。
7. 如果仍为 pending，先验证 pending 读取，再经过单独确认 prepare 并 commit 撤回。
8. 验证同一月份和申请变为 `returned`。
9. 如果提交后自动批准，跳过 MCP 撤回。不得临时改用未经实现的取消批准操作；只有在需要恢复月份可编辑状态时，才由维护者在网页手工清理。

可以选择另一个可申请月份，验证管理员批准及之后的 `approved` 月次读取；但初始发布门槛不要求这样做，因为管理员批准已经有真实证据。批准后的月份可能需要在网页手工取消批准后才能再次由员工修改。

本阶段覆盖 `LV-W03`，在条件允许时覆盖 `LV-W04`，并覆盖 `LV-R04`、`LV-S01` 和 `LV-S02` 中当前可执行的月次部分。

## 阶段 5：Playwright 登录与凭据恢复

这些测试只覆盖 Playwright 登录。不得选择 API 后端、调用 Public API、读取 OAuth 状态或测试 Token 刷新。

1. freee 自然要求 MFA、CAPTCHA 或异常登录确认时，切换到可见模式完成官方交互，验证持久 profile 恢复，即 `LV-I04`。
2. 使用一次性的 Keychain service 名称验证缺失/错误凭据指引，不触碰当前正常使用的 service，即 `LV-I05`。

## 阶段 6：已安装 Agent 验收

新的本人申请工具已经位于 `main`，但不包含在 `v0.3.3` 中。先完成源码级真实测试；只有维护者明确同意发布版本后才发布。

发布后：

1. 更新 Claude Code plugin，验证 MCP 版本、23 个工具发现、Playwright 后端和只读调用；不得调用 API 工具。
2. 在 Codex 中安装或更新用户级软件包，重复只读发现并执行一次缺少确认的拒绝测试。
3. 仅当 OpenCode 和 Pi 已经实际安装时才继续验证；不得为了填满测试矩阵安装无关软件。
4. 确认更新保留 plugin data、System Keychain 凭据和仓库外的浏览器 profile。
5. 验证文档中的回滚机制，但不得降级或删除凭据。

## 停止与恢复矩阵

| 观察结果 | 自动化处理 | 人工恢复 |
| --- | --- | --- |
| 返回预期拒绝错误 | 记录通过并继续 | 无 |
| 预览发生变化 | 没有写入；仅在案例仍需继续时重新 prepare | 审核新的预览 |
| 操作不可用 | 停止该案例 | 检查公司配置和当前状态 |
| 点击后结果不明 | 绝不重试 | 在 freee 检查准确的 No./日期，必要时手工修复 |
| 休假意外自动批准 | 停止撤回流程 | 在网页取消批准、差戻し并清理 |
| 勤務時間修正与预期不同 | 停止新的自动化 | 检查并使用事先记录的准确原值恢复 |
| 月次申请自动批准 | 跳过撤回 | 仅在必须恢复可编辑状态时手工取消批准 |
| CAPTCHA/MFA | 停止 headless 会话 | 使用可见模式完成官方交互 |

## 验收证据

将测试结果追加到真实验收清单或单独的测试运行记录中，只保存：

- 日期和测试编号；
- Git commit 和 MCP/软件包版本；
- 后端和 Agent 宿主；
- 必要时保存申请 No. 或月份；
- 仅保存指纹前 12 位，不保存完整指纹；
- 标准化结果或准确的安全错误码；
- 清理状态。

不得提交无关日期的原始时间、休假余额、完整截图、员工表格、凭据、Token、Cookie 或浏览器 profile 数据。

## 推荐执行日程

1. **会话 A，不写入：**阶段 0 和阶段 1 的 Playwright 只读/安全测试。
2. **会话 B，可撤销申请：**执行 `PA-LW` 和 `PA-LR`。
3. **会话 C，监督下修改：**执行 `PA-WT-A`，并立即执行 `PA-WT-R`。
4. **合适的月末：**执行月次提交/撤回。
5. **需要登录恢复时：**验证可见浏览器交互和一次性 Keychain 错误指引。
6. **明确批准发布后：**执行已安装 Agent 验收。
